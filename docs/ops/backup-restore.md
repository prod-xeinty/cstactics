# Бэкапы базы и восстановление (#25)

Два слоя защиты данных D1 (игроки, сессии, позже — тактики и голоса).

| Слой | Что | Глубина | Когда нужен |
|---|---|---|---|
| **Time Travel** | встроен в D1, всегда включён, бесплатно | **7 дней** (бесплатный тариф), с точностью до минуты | откатить ошибку: кривая миграция, удалили не то |
| **Ежедневный бэкап** | workflow «Бэкап D1», зашифрованный файл в артефактах GitHub Actions | **30 дней** (по одному на сутки) | пропала сама база / нужен откат дальше недели |

Видео (R2) — отдельной задачей, когда появится хранилище (#12).

## Как устроен ежедневный бэкап

`.github/workflows/backup.yml`, каждый день в 03:41 МСК (и вручную: Actions → «Бэкап D1» → Run workflow):

1. `wrangler d1 export --no-data` и `--no-schema` — **схема и данные отдельно**. Полная выгрузка D1 одним файлом идёт по таблицам в алфавитном порядке, и в пустую базу её **не восстановить**: строки `sessions` вставляются раньше, чем создана `users`. Мы склеиваем: сначала вся схема, потом все данные.
2. **Проверка восстановления**: файл выполняется в чистой базе одной транзакцией; проверяются все таблицы из `migrations/`, `integrity_check`, внешние ключи. Не восстановился — прогон красный, бэкап не сохраняется.
3. **Шифрование** (age, X25519) для публичных ключей из `security/backup-recipients.txt`. В бэкапе Steam ID и ники игроков, а артефакты публичного репозитория может скачать любой залогиненный на GitHub — поэтому только зашифрованным.
4. Артефакт `d1-backup-<id>`: `kollgg-ДАТА.sql.age` + `.sha256`. Открытый SQL на диске раннера удаляется.

Вывод `wrangler` в лог **не попадает**: `d1 export --remote` печатает подписанную ссылку на открытую выгрузку (живёт час), а логи Actions публичного репозитория видит кто угодно. При ошибке печатается только текст, ссылки вырезаны. Зависимости ставятся без установочных скриптов (`npm ci --ignore-scripts`): следующему шагу достаётся токен с правом записи в D1.

Выгрузка на время ненадолго блокирует запросы к базе — поэтому ночью.

**Каждый PR** CI гоняет `npm run backup:selftest`: та же цепочка на локальной D1 с тестовыми данными, включая восстановление в пустую D1 через `wrangler d1 execute --file`. Сломается формат выгрузки — узнаем сразу, а не в день аварии.

## Настройка (один раз)

1. **Ключ (sK8le, на своём компьютере):**
   ```
   npm run backup:keygen
   ```
   Секретный ключ сохранится в `kollgg-backup-key.txt` в домашней папке (внутрь проекта скрипт класть не даст). **Сделай копию** в менеджер паролей или на флешку: потеряешь ключ — все бэкапы превратятся в мусор. Публичный ключ (`age1…`) скрипт напечатает.
   Не держи ключ в папке, которая синхронизируется в облако (OneDrive / Google Drive).
2. **Публичный ключ** — в `security/backup-recipients.txt` отдельным PR (его можно показывать всем). Можно несколько ключей, по одному в строке — тогда открыть бэкап сможет любой из владельцев (например, и друг). Файл под CODEOWNERS: лишний ключ = кто-то третий читает все бэкапы, поэтому PR с ним ревьюим особенно внимательно. В Summary каждого прогона видны начала ключей, для которых зашифровано.
3. **Токен Cloudflare (sK8le):** https://dash.cloudflare.com/profile/api-tokens → Create Token → Custom token → право **Account → D1 → Edit** (экспорт в API Cloudflare — операция записи, одного Read может не хватить), ресурс — свой аккаунт. Отдельный токен: не аналитика и не деплой.
   У токена в Cloudflare поставь **срок действия** (например, год) и напоминание его продлить.
4. **Окружение и секреты (prod-xeinty, нужен Admin):**
   1. https://github.com/prod-xeinty/cstactics/settings/environments → New environment → `backup` → **Deployment branches and tags: Selected → `main`**. Так токен с правом записи в D1 не достанется workflow из другой ветки.
   2. В этом окружении → Environment secrets: `CF_BACKUP_TOKEN` = токен из п. 3, `CLOUDFLARE_ACCOUNT_ID`.
5. Actions → «Бэкап D1» → **Run workflow** → в Summary таблица таблиц и число строк, в Artifacts — файл. Упало с ошибкой авторизации — проверь право токена.
6. Когда первый бэкап прошёл: Settings → Secrets and variables → Actions → **Variables** → `BACKUP_REQUIRED` = `1`. С этого момента пропавший ключ или секрет — **красный** прогон (письмо), а не тихое «не настроено».

Пока чего-то нет (и `BACKUP_REQUIRED` не задан), прогон зелёный и пишет, чего не хватает.

## Восстановление

> Любое восстановление **перезаписывает** данные. Сначала остановись и запиши, что случилось и до какого момента откатываемся.

### А. Откат на момент времени (последние 7 дней) — Time Travel
```
npx wrangler d1 time-travel info kollgg                                   # ТЕКУЩАЯ закладка — сохранить ДО отката
npx wrangler d1 time-travel info kollgg --timestamp=2026-10-25T18:00:00Z
npx wrangler d1 time-travel restore kollgg --timestamp=2026-10-25T18:00:00Z
```
Сначала запиши текущую закладку (первая команда): по ней можно отменить сам откат (`restore kollgg --bookmark=…`). Подтверждение wrangler не пропускать (`--skip-confirmation` не использовать). После отката — шаг «После любого восстановления» ниже.

### Б. Из ежедневного бэкапа
1. **Только настоящий ночной/ручной прогон на `main`**: Actions → «Бэкап D1» → фильтр Branch: `main`, Event: `schedule` (или `workflow_dispatch`, если запускал сам) → нужный прогон → Artifacts → скачать `d1-backup-…` и распаковать. Прогоны из PR/форков не брать: публичные ключи открыты, зашифровать «бэкап» для них может кто угодно. Через консоль: `gh run list --workflow backup.yml --branch main --event schedule`.
2. Проверить целостность: `sha256sum -c kollgg-ДАТА.sql.age.sha256` (на Windows: `certutil -hashfile kollgg-ДАТА.sql.age SHA256` и сравнить вручную).
3. Расшифровать (команду — в папке проекта, **результат — вне проекта**, скрипт иначе откажется):
   ```
   npm run backup:decrypt -- kollgg-ДАТА.sql.age C:\Users\<ты>\kollgg-backup-key.txt C:\Users\<ты>\Downloads\kollgg-ДАТА.sql
   ```
   **Просмотреть файл** перед восстановлением: только `CREATE` / `INSERT` / `PRAGMA defer_foreign_keys`, никаких `DROP`/`DELETE`/`UPDATE`; поиск `'admin'` и `'moderator'` — только те, кто должен быть.
4. **Восстанавливать в новую базу**, а не поверх старой:
   ```
   npx wrangler d1 create kollgg-restore
   npx wrangler d1 execute kollgg-restore --remote --file kollgg-ДАТА.sql
   npx wrangler d1 execute kollgg-restore --remote --command "SELECT COUNT(*) FROM users"
   ```
5. Шаг «После любого восстановления» (ниже) — на `kollgg-restore`.
6. Проверить, что таблица `d1_migrations` на месте (`SELECT * FROM d1_migrations`): иначе `db:migrate:remote` попробует применить миграции заново.
7. Если данные верные — вписать `database_id` новой базы в `wrangler.jsonc` (PR), задеплоить, проверить `/api/health`. Старую базу не удалять, пока не убедились, что всё работает.
8. **Удалить расшифрованный `.sql`**: в нём открытые данные игроков. Не коммитить, не пересылать.

### После любого восстановления (и А, и Б)
Восстановление возвращает **старые сессии и роли**: оживут сессии, из которых игроки вышли после момента бэкапа (украденная cookie, чужой компьютер), и роли moderator/admin, которые успели снять. Если откатываемся из-за взлома — это вернёт атакующему доступ. Поэтому до переключения на восстановленную базу:
```
npx wrangler d1 execute <база> --remote --command "DELETE FROM sessions"
npx wrangler d1 execute <база> --remote --command "SELECT id, nickname, role FROM users WHERE role <> 'user'"
```
Все войдут заново через Steam; лишние роли — вернуть в `user`.

### Учения
Раз в месяц: пункт Б целиком на свежем бэкапе (до шага 6 — в базу `kollgg-restore`, потом удалить её: `npx wrangler d1 delete kollgg-restore`). Имя отличается от боевой `kollgg` одним суффиксом — **перечитай имя** и не пропускай подтверждение wrangler. Записать дату в комментарий к #25 / заметку в журнале.

## Персональные данные
Бэкапы содержат Steam ID и ники и лежат на серверах GitHub и Cloudflare за пределами РФ — учесть в политике конфиденциальности (#27). Срок хранения — 30 дней, дальше GitHub удаляет артефакты сам.
