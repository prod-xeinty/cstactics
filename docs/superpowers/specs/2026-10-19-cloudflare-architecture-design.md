# Архитектура КОЛЛ.GG на Cloudflare

Статус: согласовано  
Дата: 2026-10-19  
Целевая аудитория: игроки Counter-Strike 2 из России и СНГ

## 1. Цели и ограничения

КОЛЛ.GG — сайт с готовыми сценариями раундов для CS2. Первый релиз ограничен картой Dust2 и должен поддерживать каталог тактик, Steam-вход, определение уровня FACEIT, голосование по группам игроков, отправку пользовательских тактик с видео и модерацию.

Главные технические приоритеты:

1. Минимальные постоянные расходы на старте.
2. Возможность обслуживать большой объём читающего трафика.
3. Безопасная работа с пользовательским контентом.
4. Возможность покинуть Cloudflare без полного переписывания приложения.
5. Работа маленькой команды через ветки, Pull Request и автоматические проверки.

Осознанный риск: российские провайдеры могут ограничивать трафик к инфраструктуре Cloudflare. Этот риск принимается, но для него предусматриваются резервные копии, переносимые интерфейсы и сценарий запуска на российском VPS.

## 2. Архитектура

~~~text
Пользователь
    |
Cloudflare Worker
    |- Next.js + vinext
    |- серверные маршруты/API
    |- Steam OpenID
    |- FACEIT API client
    |
    +-- D1: пользователи, сессии, тактики, голоса, модерация
    +-- R2 private: новые видео до модерации
    +-- R2 public: опубликованные видео
    +-- Queues: фоновые задачи и повторные попытки
    +-- Durable Objects: строгие лимиты частоты операций
~~~

Приложение разворачивается как один модульный монолит. Отдельные микросервисы, Kubernetes и внешний брокер сообщений в MVP не используются.

## 3. Технологический стек

- Next.js, React и TypeScript.
- vinext как рекомендуемый Cloudflare способ запуска нового Next.js-приложения на Workers.
- Cloudflare Workers для серверного рендеринга и API.
- Cloudflare D1 как основная SQL-база.
- Drizzle ORM и явные SQL-миграции.
- Cloudflare R2 для видео.
- Cloudflare Queues для фоновых задач.
- Durable Objects для согласованных счётчиков rate limit.
- Cloudflare Turnstile для защиты публичных форм.
- Zod для общей клиентской и серверной валидации.
- Vitest с Cloudflare Vitest Plugin.
- Playwright для сквозных сценариев.
- GitHub Actions и Wrangler для CI/CD.

Обычные команды Next.js сохраняются наряду с vinext. Бизнес-логика не должна напрямую зависеть от Cloudflare bindings.

## 4. Модули

~~~text
src/
|- auth/          Steam OpenID и сессии
|- users/         профиль, роли и права
|- faceit/        профиль FACEIT и обновление ELO
|- tactics/       каталог и карточки тактик
|- ratings/       голоса и агрегированные оценки
|- submissions/   пользовательские анкеты
|- moderation/    проверка и публикация
|- media/         загрузка и выдача видео
|- patches/       версии CS2 и предупреждения
|- db/            схема D1 и миграции
|- platform/      адаптеры Cloudflare и переносимые интерфейсы
+- shared/        типы, схемы и общие утилиты
~~~

Каждый модуль предоставляет небольшой публичный интерфейс. Обработчики HTTP не обращаются к D1, R2 или Queue напрямую: доступ выполняется через сервисы домена и интерфейсы платформы.

## 6. Потоки данных

### Вход

1. Пользователь начинает вход через Steam.
2. Worker создаёт одноразовое состояние и перенаправляет на Steam.
3. Callback проверяет return_to, claimed_id, response_nonce и check_authentication.
4. Пользователь создаётся или обновляется в D1.
5. Создаётся серверная сессия.
6. FACEIT-профиль ищется синхронно с коротким таймаутом.
7. При недоступности FACEIT вход завершается, а обновление ставится в Queue.

Пользователь с неподтверждённым FACEIT может просматривать сайт, но не может голосовать в основной шкале.

### Голосование

1. Проверяются сессия, CSRF и rate limit.
2. Определяется актуальная FACEIT-группа.
3. Голос создаётся или изменяется по UNIQUE(user_id, tactic_id).
4. rating_stats обновляется в той же логической операции.
5. Клиент получает новый D1 bookmark и сразу видит собственное изменение.

Периодическая задача пересчитывает агрегаты из votes и исправляет расхождения.

### Отправка тактики

1. Сервер валидирует анкету и создаёт tactic со статусом draft.
2. Сервер генерирует ключ объекта и короткоживущую подписанную ссылку R2.
3. Браузер загружает файл напрямую в приватный бакет.
4. Клиент подтверждает окончание загрузки.
5. Queue проверяет размер, MIME, сигнатуру файла и ожидаемый объект.
6. Тактика переходит в pending.
7. Модератор принимает или отклоняет материал.
8. После принятия видео становится публичным, а тактика получает published.

### Каталог

Публичные запросы используют D1 read replication и могут начинаться с first-unconstrained. Запросы после записи используют Sessions API и bookmark, обеспечивая read-your-own-writes.

## 7. Безопасность

### Сессии

Cookie называется __Host-session и имеет HttpOnly, Secure, SameSite=Lax, Path=/ и ограниченный срок жизни. Сессия меняется после входа и изменения роли, удаляется при выходе и хранится в D1 только в виде хеша.

### Защита запросов

- Проверка Origin для всех изменяющих запросов.
- CSRF-токен для форм и API записи.
- Turnstile для входа, голосования и отправки тактики.
- Rate limit по пользователю и IP.
- Idempotency key для голосования, публикации и подтверждения загрузки.
- Серверная проверка ролей на каждом административном действии.
- CSP и стандартные защитные HTTP-заголовки.
- Запрет рендеринга пользовательского текста как HTML.

### Секреты

Steam, FACEIT, R2 и deploy-секреты хранятся только в Workers Secrets или GitHub Actions Secrets. Они не помещаются в wrangler-конфигурацию, исходный код, клиентский bundle и логи.

### Видео

- Ключ объекта создаёт сервер.
- Подписанный URL разрешает только один тип операции и имеет короткий срок.
- Ограничиваются Content-Type и CORS origin.
- Проверяются размер, MIME и magic bytes.
- Неодобренные объекты никогда не доступны через публичный бакет.
- Тяжёлое транскодирование не выполняется внутри Worker.

## 8. Ошибки и повторные попытки

- FACEIT недоступен: профиль получает pending, Queue повторяет запрос с задержкой.
- Steam не подтвердил ответ: сессия не создаётся.
- R2 недоступен: анкета остаётся черновиком, загрузку можно повторить.
- Queue-задачи идемпотентны и после исчерпания попыток переходят в dead-letter queue.
- Ошибка публикации не делает тактику публичной частично.
- Ошибка обновления рейтинга инициирует фоновую сверку агрегатов.
- Превышение 70% бесплатных лимитов создаёт предупреждение владельцам проекта.

## 9. Переносимость и резервное восстановление

Cloudflare изолируется интерфейсами:

~~~ts
interface Database {}
interface ObjectStorage {}
interface JobQueue {}
interface RateLimiter {}
~~~

Первая реализация использует D1, R2, Queues и Durable Objects. Резервная реализация может использовать PostgreSQL, любое S3, BullMQ и Valkey.

Раз в сутки:

1. D1 экспортируется в зашифрованную резервную копию.
2. Новые R2-объекты копируются во второе S3-хранилище в СНГ.
3. Проверяется целостность резервных копий.
4. Регулярно выполняется тестовое восстановление.

Начальная цель: RPO не более 24 часов и RTO несколько часов. После появления постоянной аудитории поднимается резервный VPS в России и сокращается интервал репликации.

При длительной недоступности Cloudflare приложение запускается как обычный Next.js/Node.js сервис, данные восстанавливаются в PostgreSQL и S3, а DNS переключается на прямой origin без Cloudflare Proxy.

## 10. Тестирование

### Unit

Vitest проверяет:

- определение FACEIT-группы;
- расчёт рейтингов;
- права доступа;
- переходы статусов;
- Zod-схемы;
- idempotency;
- построение ключей объектов.

### Integration

Cloudflare Vitest Plugin запускает тесты в Workers runtime с локальными D1, R2, Queues и Durable Objects. Steam и FACEIT имитируются через MSW. Проверяются миграции с пустой базы и с предыдущей версии схемы.

### End-to-end

Playwright проверяет:

- каталог и фильтры;
- вход с тестовой сессией;
- голосование и изменение голоса;
- отправку анкеты;
- загрузку видео;
- одобрение и отклонение модератором;
- недоступность неопубликованного материала;
- мобильную вёрстку и навигацию с клавиатуры.

Реальный Steam callback отдельно проверяется на staging.

## 11. CI/CD

~~~text
feature branch
-> Pull Request
-> lint, typecheck, tests, production build
-> preview
-> review
-> merge в main
-> staging
-> smoke tests
-> ручное подтверждение
-> production
~~~

GitHub Actions использует официальный Wrangler Action и минимально необходимый Cloudflare API token.

Миграции выполняются по expand/contract:

1. Добавляются совместимые поля и таблицы.
2. Разворачивается новый код.
3. Старые поля удаляются отдельным релизом.

При ошибке Worker откатывается на предыдущую версию. Совместимая миграция не откатывается автоматически.

## 12. Границы MVP

В MVP входят:

1. Главная и каталог Dust2.
2. Фильтры по стороне, составу, экономике и FACEIT-группе.
3. Полная карточка тактики.
4. Steam-вход и определение FACEIT.
5. Голосование по works и easy.
6. Экран «Под твоё эло».
7. Отправка тактики с одним видео до 10 МБ.
8. Панель модератора.
9. Метка версии CS2 и предупреждение после патча.

Не входят:

- другие карты;
- комментарии и подписки;
- платежи и премиум;
- мобильное приложение;
- автоматическое транскодирование;
- рекомендации в диапазоне плюс-минус 150 ELO;
- сложная аналитика;
- Kubernetes и микросервисы.

## 13. Критерии готовности

- Незалогиненный пользователь может найти и прочитать тактику.
- Steam-пользователь видит FACEIT-группу и может изменить свой голос.
- Повторный запрос не создаёт дубликаты.
- Неодобренные тактики и видео нельзя открыть публично.
- Модератор видит неизменяемую историю решений.
- Интерфейс работает на телефоне и с клавиатуры.
- Критические потоки покрыты Playwright.
- Резервные копии D1 и R2 проходят тестовое восстановление.
- Настроено предупреждение до исчерпания бесплатных лимитов.
